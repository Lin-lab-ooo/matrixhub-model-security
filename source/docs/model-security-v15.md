## History without typing a SHA

`ModelSecurityCard` uses the existing authenticated `ListModelRevisions` and paginated `ListModelCommits` APIs. Users choose a branch or tag, then a commit labeled with its title, author time and short SHA. The request value remains the complete immutable 40-character commit ID. Full `refs/heads/...` and `refs/tags/...` values keep identically named branches and tags distinct.

Commit history has 20 entries per page. Browsing another page retains the selected immutable report; choosing another entry changes it. A selected commit outside the current page remains explicitly labeled. Search is limited to the current page. Loading, empty history, read-permission errors and retry have separate UI states. The existing model read permission controls both history and evidence; the selector grants no write permission.

Changing a revision clears the historical-report override and rescan dialog. A new query hides the former overview, identity and evidence while loading, including refreshes of cached branch/tag results. A response with a different immutable SHA is rejected for display. The visible complete commit ID, report ID and scanner generation provide the identity needed to compare evidence. This UI does not override server-side download admission.

The source changes are confined to the security feature and bilingual locale entries; generated SDKs and routes were not hand edited. Saved lint, TypeScript and Vite checks passed for UI candidate v2. Its frozen validation manifest records five security test files and 19 tests; a separate skipped-test count was not preserved, so no zero-skip claim is made. The production asset archive is identified independently from the backend image, so an old image's embedded UI cannot stand in for a new UI test.

## Bounded parallel execution

One API owns one staging area and dispatches one active batch. Native ClamAV threads operate inside that boundary. This is not horizontal API replication or permission to share staging across multiple writers. With native threads greater than one, the scanner processes an ordered sequence of byte-bounded waves, with a fixed 2 GiB aggregate wave budget, while retaining per-file, whole-batch, memory, time, archive-depth/member/ratio and cancellation limits. A wave partitions whole files; it does not split a file to bypass the full AV file-size ceiling.

Use the standard profile for small artifacts. The opt-in large-repository profile permits multiple shards, with a 1280 MiB file ceiling, 1536 MiB scanner read budget, up to 5 GiB advertised batch capacity, and one active batch. Its normal native thread choice is two; the 128 MiB archive expansion ceiling remains unchanged. CPU/RAM quotas must match the selected profile. A 100 GB or 100 GiB repository is not a supported single file, and a configured maximum is not a measured throughput result.

See the [capacity guide](../deploy/security/profiles/README.md) for exact byte values, timeout/lease settings, physical copies, retained snapshots and memory budgets. The large-repository deployment envelope reserves source data and sealed staging copies; a 5 GiB batch cap is not a total-storage peak. The competition's separate 100,000,000,000-byte synthetic VM workload has its own three-copy ext4 budget and pinned input contract. Its result must be judged from that run's actual receipt.

marker in one transaction. Getpass must disable echo or fail; explicit anonymous
`--password-stdin` is also supported. Passwords are 14–72 UTF-8 bytes without
truncation, arguments, environment or logs. Repeated initialization refuses an
existing account; later starts validate the marker without reading password
hashes or resetting it. The source has 45 passing offline contracts. Its separate

`rules_snapshot.py` imports the complete official `main.cvd`, `daily.cvd` and `bytecode.cvd`. ClamAV 1.4.6 `sigtool` must exit successfully with signature verification; the full database must also load successfully so signed internal metadata is checked against its outer header. Full byte hashes, sizes, engine identity, verification times and daily build time are recorded. The external JSON integrity manifest is unsigned; it does not replace official CVD signature verification.

Freshness is derived from verified daily database build time, never mtime or process startup. The default maximum age is seven days and can be tightened. Future timestamps and rollback are rejected. The prepared snapshot carries an absolute expiry passed to the scanner, which fails closed at expiry. Trusted host time is part of this contract. Legacy `SCAN_RULES_EXPIRES_AT=0` is offline compatibility, not a freshness claim; the production setup wrapper supplies an explicit verified expiry.

The measured snapshot expires at `1793168749` (2026-10-28 06:25:49 UTC). An
October 29 demonstration requires normal update/prepare, actual signature/age
checks and validation of the new generation, preserving every existing CDN
cooldown. Disabling freshness or reusing an expired green report is not renewal.

A FreshClam update is a separate one-shot network job into a new staging directory. The operator supplies the existing CDN not-before gate; the tool preserves its own hash-bound FreshClam cooldown state, enforces a minimum interval, and does not blindly retry. A failed or incomplete download cannot become active. Publication atomically switches an external pointer to a new immutable snapshot. Recreate the scanner with the new read-only directory; a changed generation invalidates previous approvals. Never update a running scanner's rules directory in place.

API/scanner runtime UID/GID is 65532. Rules are read-only, staging is API-RW/scanner-RO, and the Unix socket is 0660. Only the dedicated networkless volume initializer uses UID 0, with CHOWN/FOWNER for its owned volume roots. Runtime containers drop all capabilities and use read-only roots. The tooling does not use privileged mode or world-writable data directories. Temporary tool containers have exact ownership and cleanup; failed startup stops only the owned project and preserves its data.

The large bind-directory profile additionally requires a real low-UID POSIX seal/hash/stable-FD preflight. This machine's Windows/exFAT G bind allowed write/fsync but rejected `fchmod(0440)` with EPERM. It is therefore rejected with a fixed diagnostic and a Linux/ext4 recommendation; the tool does not chmod777 or migrate Docker data. G can hold public inputs, tooling and a VM image, while the application's large data path must use verified POSIX storage such as ext4 inside that independent VM.

## Persistent personal demonstration

The local handoff's `runtime/optimization-v15-20261023/human-demo-v15` tools create a dedicated small personal demonstration. They preserve newly owned ext4 Docker volumes and never read, restore or reset the old six-service account. Initial migration stays unpublished; only successful fresh bootstrap permits the new product port. An account-ready checkpoint and owned database markers permit recovery after a later seed failure without resetting a password.

Automatic setup was explicitly authorized for this new instance. A random password is generated in RAM, stored as bcrypt in its database, and protected separately with Windows **CurrentUser** DPAPI in an exclusively created ciphertext file bound to the run ID. The public owner record pins that ciphertext. It is not logged, passed in arguments/environment, or included in release evidence. The explicit owner-only revealer is separate from default describe and does not recover earlier credentials. Manual human setup stores no decryptable password copy.

This is a dedicated fixture and personal login handoff, not a general Compose/Helm administrator-initialization API, production secret manager, SSO system or user signing-key lifecycle. Normal stop, controller exit and Docker restart retain the new account volumes. Sessions may expire; the same password can log in again. Deletion remains an explicit owned-data operation, not deadline cleanup. Large payloads are excluded from this small-demo storage allowance.
